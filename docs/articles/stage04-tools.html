第04回：検証コマンドとPowerShell作業導線を作る

設定項目が増えると、目視だけではミスを拾えません。そこで、configcheck、gptcheck、mixi2check、timelinecheck、postcheckなどの確認コマンドを使い、設定、OpenAI、mixi2認証、投稿読み取り、投稿可否を段階的に確認できるようにしました。

PowerShellスクリプトも重要です。人格切替、機能切替、新規人格作成、素材チェック、一括プロファイルテストをスクリプト化することで、手作業のブレを減らしました。

日本語ファイルをPowerShellで扱う時は文字化けとBOMに注意しました。GoファイルやJSONを書き換えるとき、UTF-8 BOMありで保存されると予期しない問題が出ることがあります。

後にConfig UIの一発起動batでも文字化け問題が起きました。最終的にはbatをASCIIに寄せ、表示文言を英数字中心にすることで安定させました。

確認ポイント

  • この段階で何を確認すべきかを明確にする。
  • 秘密値や実ログを公開記事に含めない。
  • 問題が起きた場合は、前段階へ戻って切り分ける。
  • 作業後は必ずGit status、ビルド、対象ページ表示を確認する。

PowerShellで避けること

PowerShellで再帰検索する時は、.git、logs、.exe を対象にしないようにします。特に生成済みexeをSelect-Stringすると、大量出力で止まったように見えることがあります。

Get-ChildItem -Recurse -File |
  Where-Object { $_.Extension -notin ".exe" -and $_.FullName -notmatch "\\.git\\" }

日本語ファイルを書き換える時はUTF-8 BOMなしを使います。これはGoファイル、JSON、HTML、CSSすべてで安全側に倒すための運用です。

実作業の分解

検証コマンドは、障害調査の順番を固定するための道具です。configcheckで設定を見る、gptcheckでOpenAIを見る、mixi2checkで認証を見る、timelinecheckで読み取りを見る、postcheckで投稿を見る。この順番にすると、どこで失敗しているか分かりやすくなります。

PowerShellスクリプトは便利ですが、文字コードと対象ファイルに注意します。日本語を含むファイルを壊さない、.exeや.gitを検索対象にしない、git add . を安易に使わない、というルールが重要です。

この段階で大事なのは、作業結果を「動いた」「動かない」だけで判断しないことです。どの入力に対して、どの設定を読み、どの外部サービスへ接続し、どのログへ残るのかを確認します。BOTは一度動くと自動で投稿・返信するため、目に見える成功よりも、誤作動しないための確認が重要です。

また、ローカルで成功した作業とRailwayで成功した作業は分けて扱います。ローカルでは.envを読みますが、本番ではRailway Variablesを読みます。ローカルではファイルが残っていても、本番ではVolumeがなければ再デプロイで状態が消える可能性があります。この差を毎回意識します。

作業後は、Gitの差分、ビルド結果、確認コマンド、必要ならブラウザ表示を確認します。特に公開ノート側では、HTMLのリンク切れ、スマホでの横はみ出し、モック画像の表示、詳細記事の前後ナビを確認します。
