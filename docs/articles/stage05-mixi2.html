第05回：OpenAI APIとmixi2 Pluginにつなぐ

ローカル構造が整ったら、OpenAI APIとmixi2 Pluginへ接続します。OpenAI側ではAPIキー、モデル、画像生成の有効/無効を確認し、mixi2側ではClient ID、Client Secret、Community ID、Requirementを確認します。

mixi2では、これはBotアプリではなくコミュニティ用Pluginです。Developer PlatformでRequirementを設定し、Application Versionを更新し、対象コミュニティへインストールまたは再許可する必要があります。

Requirementが不足していると、timelinecheckでPermissionDeniedになります。コードが正しくても権限が反映されていないと動きません。

この段階では、mixi2checkで認証とrequirementsを見て、timelinecheckで投稿取得を確認し、postpreviewとpostcheckで投稿内容と投稿可否を確認しました。

確認ポイント

  • この段階で何を確認すべきかを明確にする。
  • 秘密値や実ログを公開記事に含めない。
  • 問題が起きた場合は、前段階へ戻って切り分ける。
  • 作業後は必ずGit status、ビルド、対象ページ表示を確認する。

Requirement変更後の確認順序

Requirementを変更したら、Developer Platformで設定しただけでは終わりません。Application Versionを更新し、対象コミュニティで再インストールまたは再許可し、mixi2check のrequirementsに反映されたことを確認します。

go run ./cmd/mixi2check
go run ./cmd/timelinecheck
go run ./cmd/postcheck

timelinecheckでPermissionDeniedが出る場合、コードより先にRequirementと再許可を疑います。

実作業の分解

mixi2 Plugin接続では、Client IDやSecretだけでなく、RequirementとApplication Versionが重要です。Requirementを変えても、コミュニティ側で再許可されていなければ、Pluginは新しい権限で動きません。

timelinecheckが失敗する場合は、コードより先にRequirementを疑います。postcheckが失敗する場合は、投稿権限、Community ID、認証情報を順番に確認します。

この段階で大事なのは、作業結果を「動いた」「動かない」だけで判断しないことです。どの入力に対して、どの設定を読み、どの外部サービスへ接続し、どのログへ残るのかを確認します。BOTは一度動くと自動で投稿・返信するため、目に見える成功よりも、誤作動しないための確認が重要です。

また、ローカルで成功した作業とRailwayで成功した作業は分けて扱います。ローカルでは.envを読みますが、本番ではRailway Variablesを読みます。ローカルではファイルが残っていても、本番ではVolumeがなければ再デプロイで状態が消える可能性があります。この差を毎回意識します。

作業後は、Gitの差分、ビルド結果、確認コマンド、必要ならブラウザ表示を確認します。特に公開ノート側では、HTMLのリンク切れ、スマホでの横はみ出し、モック画像の表示、詳細記事の前後ナビを確認します。
